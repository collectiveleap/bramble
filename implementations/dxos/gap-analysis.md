# Gap analysis — X = DXOS / Composer (whole-system)

This gap analysis evaluates the DXOS ECHO substrate and the Composer product against the Bramble Specification of Internal Primitives (SIP, judged at data-model/invariant altitude) and Specification of User Primitives (SUP, judged at user-observable altitude). Every verdict below is drawn from the adjudicated, verifier-reviewed result set; each rests on cited `file:line` evidence. One verdict (IP-2.multi-predecessor) was adjudicated `pass` but did **not** survive adversarial review; per the guide's Tana exemplar (`gap-analysis-guide.md:34`, owner+reference = divergent) it is **resolved to `divergent`** throughout. The adjudicator's initial `pass` is preserved in the per-req note because the pass-vs-divergent tension is itself a top spec-improvement finding (§6).

## 1. Framing — what DXOS provides at substrate vs product level

**Substrate (ECHO).** ECHO is a typed-entity graph substrate. It reifies exactly three entity kinds via `EntityKind` — `Object`, `Relation`, `Type` (`packages/core/echo/echo/src/internal/common/types/entity.ts:124-128`) — so its connections are **not uniform**. There are three structurally distinct connection mechanisms:

- **Structural containment** — inline nested records owned by exactly one ECHO root via the `EchoOwner` symbol, plus the single-parent ownership tree (`ParentId`). These are the *only* connections subject to a hard acyclicity / single-inbound-owner invariant (`ownership.ts:13-21`; `typed-handler.ts:352-357`; `Obj.ts:703-739`).
- **Ref** — a lazy directed *pointer* held as a property value (`ref.dxn`/`ref.uri`), not a reified entity, with arbitrary fan-out; cyclic Refs are explicitly allowed (`Ref.ts:22-41`; `ownership.ts:17`).
- **Relation** — a first-class, id-bearing, typed, directed edge with `Source`/`Target` endpoints and its own properties (`Relation.ts:26-45,155-183`).

Every authored content unit is an `Obj` of `EntityKind.Object` carrying its own ULID `EntityId` (`Obj.ts:172-212`; `entity-id.ts:99-103`), unique within a space (`EID.ts:118-124`). Identity is content-independent and survives edits, moves, and serialization round-trips (`Obj.ts:142-153,366-368`; `json-serializer.ts:94-111`). The substrate provides reverse traversal as a first-class capability — `Query.referencedBy` over Refs (`Query.ts:62-83`) backed by `ReverseRefIndex` (`reverse-ref-index.ts:68-133`), and `targetOf`/`sourceOf` over Relations (`Query.ts:91-117`). Cyclic Refs and cyclic Relations are unconstrained; only inline containment and single-parent ownership are kept tree/acyclic. The finest addressable unit is the **whole entity** — `echo://<spaceId>/<objectId>` carries no sub-object/property-path/fragment component (`EID.ts:14-18`; `DXN.ts:16-31`).

**Product (Composer).** Composer's surfaces split sharply by content model. **First-class-object surfaces** (Stack/Collection, Board, Table, Kanban, Sketch, File) compose whole ECHO objects by Ref or by query, so multi-location and per-object addressing work. The user-facing **linking UI is concentrated in markdown**: the `@` popover and slash menu insert an inline link `[label](dxn)` or a block embed `![label](dxn)` carrying `Obj.getURI(object)` (`useLinkQuery.ts:31-90`). The block embed is a true **edit-through, on-demand transclusion** — it portals the live object's Section surface, the same component used standalone (`MarkdownEditor.tsx:272-284`; `react-surface.tsx:40-55`). A backlinks **Related** companion panel exists (`RelatedArticle.tsx:23-41`), auto-populated by `useRelatedObjects`. Critically, the one **outline-structured** surface — the Outliner — stores its content as a single `Ref(Text.Text)` blob; rows are CodeMirror-decorated markdown lines with no per-row ECHO identity (`Outline.ts:12-19`; `outliner.ts:94-119`). No surface mints a URI below whole-object granularity.

## 2. Per-requirement findings

### IP-1.content — SIP — **pass** (confidence: medium)
Every authored content unit materializes as an `Obj` of `EntityKind.Object`, the single content-vertex discriminator (`Obj.ts:217-220`; `entity.ts:121-130`); `Relation` is a directed edge that rejects `ParentId` (`Relation.ts:26-45,155-183`) and `Type` is meta. First-class nesting is provided by the parent tree (`Obj.ts:703-739`) and Collection-by-Ref (`Collection.ts:17-28`), with inline records (`ownership.ts:13-21`) being the opaque-part case that nesting is *not*. Text is an ordinary `Obj` of type `org.dxos.type.text` (`Text.ts:11-26`).
- **What would raise to high:** Enumerate all registered Composer content schemas (sketch shapes, table cells, file bytes) via `dxos-introspect list_schemas` and confirm each materializes content as an `Obj` of `EntityKind.Object` rather than on a Relation or non-Obj carrier; the universal "no content type bypasses Obj" claim currently rests on the EntityKind partition plus Text/Obj/Collection inspected directly.
- **Probe — smallest independently-identified unit (container or element?):** A nested element. The smallest unit is the `Obj`, which bears its own `EntityId` at any nesting depth; a child attached via `setParent` is a full, independently-addressable vertex.
- **Probe — one content vertex kind or several disjoint types?:** One kind (`EntityKind.Object`), many content *types* differentiated by schema; Relation/Type are edge and meta, not disjoint content vertices.

### IP-1.content-type — SIP — **pass** (confidence: high)
`Obj.make` asserts only `kind === Object` with no content-type whitelist (`Obj.ts:172-212`), so the content-type set is open by construction; new types are schema declarations via `Type.makeObject`, not substrate changes. Non-text first-class content is demonstrated by Sketch/Canvas, whose content is an opaque `Record(String,Any)` tldraw store (`Sketch.ts:15-40`), created by the identical path as text content (`Text.ts:11-26`). Identity, Ref/Collection linking, parent nesting, and backlinks are all defined on `Obj` generically with no content-type branch (`entity-id.ts:99-103`; `Collection.ts:20-26`; `reverse-ref-index.ts:68-72`).
- **What would raise to high:** N/A (already high).
- **Probe — can a unit hold non-text content as a first-class unit?:** YES — Sketch/Canvas (drawing) and plugin-file (blob) via the identical `Type.makeObject`/`Obj.make` path; the content-type set is open.
- **Probe — do identity/nesting/linking/backlinks/embedding behave the same for non-text?:** YES at substrate level — all defined on `Obj` generically. ("interactive widget"/"audio clip" as named in the req are not located as shipping schemas — UNVERIFIED as concrete types — but this does not affect the open-set invariant.)

### IP-1.typed-node — SIP — **pass** (confidence: high)
*(Added 2026-07-11 via the typed-Node move-up — see `plan/2026-07-11-typed-node-accommodation-design.md`; code-evidenced + live-confirmed, not part of the original adjudicated set.)* ECHO's typed objects are ordinary `Obj`s of `EntityKind.Object` bearing a schema (`Type.makeObject`; `Obj.make` imposes no content-type/schema whitelist, `Obj.ts:172-212`), so a typed Node carries full identity/edges/addressing exactly as an untyped one (see `IP-1.content-type` above). Typing is **additive** — a schema is the object's own property, not a separate object space: the Create Object picker's types (Document, Table, Sketch, Person, Outline) all materialize as first-class addressable `Obj`s (confirmed live 2026-07-11 — an Outline object has its own URI and object-level "Copy link"). The accommodation invariant holds: typing does not move a Node out of the outline/graph.
- **Probe — can a Node carry a named type with typed fields?:** YES — schema-typed objects via `Type.makeObject`; the type is the object's schema.
- **Probe — typed Nodes addressable/nestable/linkable/embeddable as untyped?:** YES — all defined on `Obj` generically, independent of schema.
- **Probe — add/remove type preserves identity and edges?:** YES at substrate — `EntityId` is schema-independent (`IP-1.stable-identity`); a schema-change gesture was not exercised live (that leg UNVERIFIED), but the id is content/edge/schema-independent by construction.

### IP-1.identity — SIP — **pass** (confidence: medium)
Every `Obj` receives a ULID `EntityId` at creation (`create-object.ts:100`; `entity-id.ts:14-17,116-118`), unique within a space (`EID.ts:116-128`), with a resolvable URI (`Obj.getURI`, `Obj.ts:512-515`). Deletion is a tombstone marker, not id reclamation (`deleted.ts:8-19`); new objects draw fresh ULIDs with no free-list.
- **What would raise to high:** In a running Composer, soft-delete a Node then attempt to resolve its `EntityId` via the query layer (does the URI still resolve to the tombstone?), and attempt to re-create an object supplying the tombstoned id via `Obj.make` `MakeProps.id` (is reuse rejected?). Also confirm whether the spec's "store" maps to one space or a multi-space store, fixing the uniqueness grain.
- **Probe — per-unit or only top-level containers?:** Per-unit — a ULID `EntityId` is assigned to *every* `Obj` at creation, including any nested/successor Node.
- **Probe — unique across the whole store?:** Unique across the ECHO space (`EID.ts:121`); across multiple spaces the space-qualified `echo://<spaceId>/<objectId>` form is the cross-space-unique identifier. If "store" == one space, store-wide uniqueness holds outright.
- **Probe — can a deleted id be reassigned?:** No accidental reassignment (tombstone, no free-list); deliberate reuse via caller-supplied `MakeProps.id` was not confirmed blocked (UNVERIFIED).

### IP-1.stable-identity — SIP — **pass** (confidence: high)
The `EntityId` is fixed at creation as a content-independent random ULID (`Obj.ts:142-153,172-212`; `entity-id.ts:116-118`); content mutation flows through `update`, which touches props only, never the id (`Obj.ts:336-368`). Re-parenting writes `entity[ParentId]` on the same instance (`Obj.ts:721-739`); adding/removing Refs or Relations never rewrites the target's id (`Ref.ts:22-41`; `Relation.ts:155-183`). The serializer exports/imports via `Obj.toJSON`/`fromJSON`, emitting the id, requiring it on import, retaining it through decode, and validating rather than regenerating it (`serializer.ts:82-96`; `json-serializer.ts:58,65,94,99-108,111`; `Json.test.ts:168,173`).
- **What would raise to high:** N/A (already high).
- **Probe — survives content edits + save round-trip?:** YES, both halves — id immutable under `update`; serializer preserves and validates the id across the persistence boundary.
- **Probe — survives move / gaining an additional location?:** YES — re-parent writes `ParentId` on the same instance; a Ref/Relation addresses the target by DXN and never rewrites its id.

### IP-2.direction — SIP — **pass** (confidence: high)
`Relation` is a reified `EntityKind.Relation` entity with exactly one `Source` and one `Target` slot stored as distinct symbols/URIs (`Relation.ts:26-45,112-116,155-183`), read back via distinct `getSource`/`getTarget` and exposed asymmetrically by `Query.sourceOf`/`targetOf` (`Query.ts:91-117`). Independently, the single-parent back-link (`Obj.ts:703-739`) is told apart by `getParent` (up) vs `children()` (down) (`Query.ts:118-129`). Predecessor→successor is distinguishable from its reverse.
- **What would raise to high:** N/A (already high).
- **Probe — directed edges or opaque child-list/folder nesting?:** BOTH — a reified directed-edge model (`Relation`) plus child-list (`Collection`) and directed back-link (`Parent`); the directed-edge model satisfies IP-2.direction.
- **Probe — can the two endpoints be told apart by direction?:** YES — distinct Source/Target slots and accessors for `Relation`; `getParent` vs `children()` for `Parent`.

### IP-2.multi-predecessor — SIP — **divergent** *(resolved per guide convention; adjudicator initially returned `pass`)* (confidence: medium)
The adjudicated verdict was **pass**: one object can be a member of two distinct Collections via two independent Refs (`Collection.ts:20-26`), Refs carry no exclusivity (`ownership.ts:13-21`), and multiple Relations may target the same object with no uniqueness constraint (`Relation.ts:155-183`); all locations resolve to one shared vertex (`Obj.ts:756-758`), with the inbound predecessor set recoverable via `referencedBy`/`targetOf` (`Query.ts:78-83,102-105`).
- **VERIFIER NOTE (axis failures: overlooked-equivalent, altitude, inference):** The controlling `gap-analysis-guide.md` pre-classifies this exact mechanism as **divergent** ("owner + reference, not multi-predecessor edges"; Tana exemplar at guide:34). The Ref/Collection candidate *is* owner+reference, so the convention names it divergent on this very req; the verdict reaches "pass" only by overriding cl.1 then-clause-sufficiency, and itself concedes this would revise the Tana exemplar. The verifier further notes ECHO has no type-distinct *structural* edge (no predecessor/successor kind), and no Composer surface renders Relation `sourceOf`/`targetOf` as outline nesting, so then[1] ("S appears beneath each … in the outline") is not satisfied as a structural-outline invariant. The capability (one shared vertex in many containers) genuinely exists, but via owner+reference and generic relations — the textbook divergent pattern.
- **2026-07-11 SIP-reword re-review:** `IP-2.multi-predecessor` then[1] was reworded from *"S appears beneath each … in the outline"* to the pure-structural *"S is a structural successor of both P1 and P2"* (outline rendering deferred to the SUP; adopts §6). Re-review: verdict **unchanged — divergent.** ECHO still has no *distinguished structural* edge (Relations are generic; Collections/Refs are owner+reference), so "structural successor" is not natively satisfied; the reword removes the rendering-dependency ambiguity, not the divergence.
- **What would raise to high:** In a running Composer, exhibit one object O placed as a structural successor of two distinct predecessor Nodes simultaneously and confirm both render O "beneath each" with edit-through.
- **Probe — one unit under more than one container, or one-parent only?:** YES, multi-container — one object can be a member of two Collections via two Refs, and two Relations may target it; not limited to one parent for the Ref/Relation graph.
- **Probe — several places = one unit or copies?:** ONE unit — Refs compared by target uri; every location resolves to the same vertex.

### IP-2.shared-identity — SIP — **divergent** (confidence: medium)
Capability delivered via Ref-to-shared-entity membership containers (`Collection.objects` / `Board.items` = `Array(Ref(Obj.Unknown))`, `Collection.ts:20-26`; `Board.ts:14-29`) resolving by `EntityId` to one in-place-mutable entity (`ref.ts:352-354,522-529,718-725`; `Obj.ts:366-368,429-430`; `EID.ts:118-124`), **not** via the spec's first-class multi-predecessor structural-edge model. ECHO has no structural-edge entity: the parent relation is single-parent, inline containment forbids multiple inbound pointers, and Relations do not carry the edit-propagation invariant. The traced SUP capability holds at user-observable altitude: the same object rendered in multiple Ref locations is edit-through across Stack/Collection sections (`StackArticle.tsx:40,49-50`), multiple Boards (`Board.ts:14-29`), and markdown block embeds (`MarkdownEditor.tsx:272-284`). Matches the guide's Tana exemplar — "owner + reference instead of multi-predecessor edges."
- **Actual mechanism:** owner + reference (membership-by-Ref to one EntityId-keyed in-place-mutable entity), not multi-predecessor edges.
- **What would raise to high:** In a running Composer, place one ECHO object into two Ref containers, open both, edit content in one, and confirm the change is observed live in the other without reload — verifying the `Obj.update` → atom-subscription → re-render path at the UI for every Ref location (the reactive path left untraced).
- **Probe — editing in one place updates all, or independent copies?:** One vertex. Multi-location is non-owning Refs resolving by URI to the single EntityId-keyed live entity; `Obj.update` mutates that one entity in place. NOT copies. (End-to-end UI re-render asserted at substrate altitude but not line-cited.)

### IP-2.acyclic — SIP — **fail** (confidence: high)
The single hard, write-time acyclicity invariant applies only to the inline-record containment subgraph (`wouldCreateCycle` → "Cannot create cycles in typed object graph. Consider using Ref for circular references." — `ownership.ts:13-21,185-186`; `typed-handler.ts:352-356`), which enforces single-inbound-owner and is therefore a tree, incapable of being the multi-predecessor structural edge. For every multi-predecessor-capable mechanism there is **no** transitive self-nesting prevention: cyclic Refs are explicitly allowed (`ownership.ts:17`; `Ref.ts:25-26`), `Relation.make` does no ancestor check (`Relation.ts:155-183`), and `setParent`'s cycle guard is explicitly short-circuited (`typed-handler.ts:348-350`) with no ancestor check in `setParent` (`Obj.ts:732-739`). A structural unit can be made its own transitive ancestor.
- **What would raise to high:** N/A (already high).
- **Probe — prevent a unit nested transitively inside itself?:** Only for the single-owner inline-record subgraph; for Ref/Collection, Relation, and parent there is no transitive self-nesting prevention.
- **Probe — can outline expansion run away?:** Termination is only a defensive traversal tactic (visited/seen Sets in `traverseObjectGraph` and the parent walk), not a graph invariant; the Ref/Relation/parent structural graph can contain cycles, so "following successor edges terminates" does not hold structurally.

### IP-3.cross-reference — SIP — **pass** (confidence: high)
A `Ref` is a directed property-value pointer that resolves via `ref.dxn` to any Obj/Relation/Type but sets no `ParentId` and adds nothing to `Collection.objects` (`Ref.ts:22-70`); outline/containment is carried separately by the parent tree and Collections (`Obj.ts:703-739`). The acyclicity/single-owner invariant governs only inline containment and explicitly exempts cyclic Refs (`ownership.ts:13-21`), confirming Ref is type-distinct from the structural edge. `Relation` (with `ParentId` asserted undefined, `Relation.ts:165`) is a second, reified form. Forward traversal is kept typed apart from structural traversal (`Query.ts:62-83`).
- **What would raise to high:** N/A (already high).
- **Probe — lightweight cross-reference distinguished from containment?:** YES — a Ref resolves to the target but sets no `ParentId` and nests nothing; referencing does not nest.
- **Probe — reference any unit, referrer's outline untouched?:** YES — a Ref (or `Ref.Array`) can target any entity, imposing no `ParentId`/membership; a Relation likewise connects any two objects with `ParentId` undefined.

### IP-3.may-cycle — SIP — **pass** (confidence: medium)
Two units can reference each other; X does not reject the reciprocal reference. The ownership-layer invariant explicitly allows cyclic Refs (`ownership.ts:17`), and the only write-time cycle guard applies to the inline owned-record subgraph and names Ref as the sanctioned escape (`typed-handler.ts:352-357`). `Relation.make` asserts only schema-kind and no-parent (`Relation.ts:155-183`) — never inspecting whether the inverse edge exists — so A→B and B→A persist as two distinct reified edges.
- **What would raise to high:** In a running Composer/ECHO session, create A→B via Ref then B→A (and separately reciprocal Relations); confirm both reciprocal edges persist across a save/replication round-trip with no write-time or index-time rejection.
- **Probe — can two units reference each other, or is the reciprocal rejected?:** YES, both can; not rejected — via either Ref (cyclic Refs allowed) or two independent Relations (no pairing/uniqueness/reciprocity constraint).

### IP-3.backlinks — SIP — **pass** (confidence: high)
`referencedBy()` over a single-object selection (`Query.ts:70-83,269-277`), backed by `ReverseRefIndex.query(targetDXN)` (`reverse-ref-index.ts:86-100`), returns every holder of an incoming Ref to the anchor. The reverse set is computed by inverting holders' *outgoing* refs (`reverse-ref-index.ts:102-133`; `extractReferences` :19-45) — no stored back-edge, no authored return reference. For Relations, `targetOf()` derives incoming edges from single directed entities (`Query.ts:96-105,288-294`).
- **What would raise to high:** N/A (already high).
- **Probe — enumerate what links here for an arbitrary unit?:** YES — `referencedBy()` (Ref-backed) or `targetOf()` (Relation-backed).
- **Probe — inbound set derivable without an authored return reference?:** YES — derived by inverting holders' outgoing refs; no back-edge stored or authored.

### IP-3.expand — SIP — **pass** (confidence: medium)
The block embed `![label](dxn)` is rendered as an atomic inline block widget (`preview.ts:135-154,216-242`) that resolves `dxn → client.graph.makeRef(dxn).target` (the single live ECHO object, `Ref.ts:22-41`; `ref.ts:183-201`) and renders the identical Container used for the standalone Article (`MarkdownEditor.tsx:272-284`; `react-surface.tsx:40-55`), so edits flow to the source vertex, not a copy. Ref targets resolve lazily and the editor rebuilds only when the ref resolves (`preview.ts:94-98`), bounding cycles (which are admissible, `ownership.ts:17`).
- **What would raise to high:** In a live Composer, place a block embed of T in document A, type into the inline-rendered Section Surface and confirm (a) keystrokes persist to source T (open T standalone), and (b) embedding T inside T (or a Ref cycle) renders one level on demand without unbounded expansion or throw.
- **Probe — inline-rendered referenced unit edits the source or a copy?:** The source, one vertex — embed resolves to the single live object and renders the same Container as standalone.
- **Probe — expansion one level on demand, bounding cycles?:** YES — the widget materializes only for `![...]` markup in this document; Refs resolve lazily, so a cycle does not force unbounded resolution.

### UP-1.outline — SUP — **partial** (confidence: medium)
The Outliner renders content as a nested outline of discrete, individually focusable/selectable/deletable list items (`Outline.tsx:123-141`; `outliner.ts:94-119`) — clause (a) passes. But each row is a CodeMirror-decorated markdown line over a single `Ref(Text.Text)` blob (`Outline.ts:12-19`; `Text.ts:11-26`) with only a positional `item.index`, no `EntityId`/URI; converting a row to an addressable object is an unimplemented TODO (`outliner.ts:27`). Every user-facing link insert emits a whole-object URI (`useLinkQuery.ts:58`), and EID/DXN carries no sub-object fragment (`EID.ts:14-35`) — so clause (b), per-Node addressing of nested Nodes, **fails** uniformly (Stack sections are addressable but rendered flat, not nested; navtree nests over whole-object graph nodes, not content rows).
- **What would raise to high:** Live Composer run: open an Outline, focus a nested row, and check every row affordance (context menu, keyboard, drag) for a copy-link/get-URI gesture yielding a link to that single row rather than the whole Outline object; also inspect the Journal surface. A confirmed absence (consistent with the no-fragment EID/DXN ceiling) raises to high.
- **Probe — address/link a single bullet, or only a top-level container?:** Only the top-level container is addressable; a row has no `EntityId`/URI and is not enumerated by the picker.
- **Probe — present content as an outline of discrete actionable units?:** YES — nested, individually focusable/selectable/deletable list items, even though the rows are not independently addressable.

### UP-1.multi-location — SUP — **partial** (confidence: medium)
The data model permits one object (one `EntityId`) in N collections (`Collection.ts:20-26`; `CollectionModel.add` never removes from others, `CollectionModel.ts:22-27`), and the navtree graph builder renders each member keyed by `object.id`, so the same node renders beneath each parent Collection simultaneously (`collections.ts:144-178`; `AppNode.ts:257-258`; `NavTree.tsx:54-57`). But the user-reachable second-placement that keeps the first is **not confirmed**: the standard navtree drag is a MOVE — adds to destination, removes from source (`AppNode.ts:139-145`) — and the purpose-built co-locate `onCopy` is commented out pending native object cloning (`AppNode.ts:147-158`). The verifier confirmed the gap: same-space drags always resolve to "transfer"/move, and AddObject always constructs a new object.
- **What would raise to high:** Live Composer probe: with two Collections, file an *existing* object into a second Collection (navtree drag, any context-menu "add to"/"move", view/database AddObject) and observe whether it remains under the first while appearing under the second. If a user-reachable gesture co-locates without removing from source, raise to pass; if none exists, holds at partial.
- **Probe — one unit in more than one outline place at once?:** YES (data model + render) — one object in N collections rendered beneath each parent in the navtree.
- **Probe — does putting it in a second place show it in both?:** NOT confirmed at the user-gesture level — navtree drag is MOVE; multi-location `onCopy` disabled.

### UP-1.stable-under-edit — SUP — **pass** (confidence: medium)
The user-facing link is markdown `[label](dxn)` storing `Obj.getURI(object)` (`useLinkQuery.ts:57-65`); the stored URL is the object's URI/DXN, composed solely of `spaceId`+`entityId` (`EID.ts:72-84,98-106`), carrying no content component. Content edits go through `Obj.update`, mutating fields in place and never reassigning the id (`Obj.ts:366-368,142-153`). Move/co-locate is a membership operation (splice `collection.objects` or change parent via `setParent`, `StackArticle.tsx:63-108`; `Obj.ts:727-739`) leaving the target's id untouched.
- **What would raise to high:** In a running Composer: insert `[label](dxn)` to T in document A; (1) edit T's content and reload the space, confirm the chip still resolves to T; (2) move/co-locate T into a second collection, confirm the link still resolves to T. Observing both confirms no save/migration path rewrites the stored URI.
- **Probe — links survive content edits + save round-trip?:** YES at code-reading altitude — the URI carries no content component; `Obj.update` never reassigns the id; resolution re-fetches by DXN. (Save-round-trip leg is code-reading only — no link-rewrite path found, but that absence is an inference.)
- **Probe — links survive the unit being moved/co-located?:** YES at code-reading altitude — move/co-locate is a membership op that leaves the target's id/URI untouched.

### UP-1.any-content-type — SUP — **pass** (confidence: medium)
The user can create, link, nest, and embed non-text units through content-type-blind seams shared with text units. EMBED: block-embed renders whatever `AppSurface.Section` the target registers (Sketch and File both do — `sketch react-surface:20-23`; `file react-surface:25-27`). - **What would raise to high:** In a running Composer: create a Sketch and a File, exercise all four verbs through the same gestures as a Markdown.Document (open standalone, `@`-insert, drop ref into a Collection, `@@`-embed with edit-through), confirm parity. - **Probe — create/link/nest/embed non-text the same way as text?:** YES via content-type-blind seams. Limit: nest requires `CollectionItemAnnotation` and embed requires a Section surface — per-type opt-ins (present for Sketch and File), not a substrate-level text privilege (text Documents depend on the same seams).

### UP-2.link — SUP — **pass** (confidence: medium)
While editing a Markdown document, the `@` popover (and the "Inline link" slash command) searches every non-hidden, non-Relation registered type and inserts `[label](Obj.getURI(object))` at the cursor (`useLinkQuery.ts:31-67`; `menu-presets.ts:114-128`; `Obj.ts:512`), rendered as an inline `dx-anchor` chip resolving to T (`preview.ts:118-133`). The operation is a pure in-text insertion (`insertAtCursor`, `util.ts:7-12`) — no Ref array entry, no membership, no parent/child or successor edge; T is not nested under A.
- **What would raise to high:** Live Composer: trigger the `@` picker (or slash "Inline link"), select an existing object T, confirm (1) a non-expanded inline link chip to T appears at the cursor, and (2) the document's structure/outline is unchanged — no section, child, or membership edge to T is created.
- **Probe — link to another unit from within a unit's content?:** YES — the `@`/slash UI inserts a link carrying T's whole-object URI as an inline chip. (Note: this affordance lives on the flat-Text markdown surface; the outline-structured Outliner has no object-link affordance — `Outline.tsx:129-141`.)
- **Probe — does linking leave the referrer's outline untouched?:** YES — pure in-text insertion; no membership/parent/successor edge. On a flat-Text Markdown.Document this holds vacuously (no successor structure to disturb).

### UP-2.backlinks-view — SUP — **partial** (confidence: low)
The "Related" companion panel is presented on the focused object T (`RelatedArticle.tsx:23-41`; `companions.ts:43-57`) and auto-populates via a full-store scan (`useQuery(db, Filter.everything())`, `useRelatedObjects.ts:27`) without an authored return link. It lists objects whose *Ref properties* target T (`useRelatedObjects.ts:45-50`) plus incoming Relation endpoints (:53-72). The seam: `getReferences` enumerates only first-class Ref-typed props (`useRelatedObjects.ts:37-41`), but the user-facing inline markdown link is stored as text inside the source's Text blob (`Markdown.ts:26`; `useLinkQuery.ts:58,78`), so links authored via the user-facing UI plausibly do **not** feed the view. The substrate `referencedBy`/`ReverseRefIndex` exists but is not wired to this UI (`Query.ts:70-83`; `reverse-ref-index.ts:68-97`; self-flagged TODO at `useRelatedObjects.ts:18`).
- **What would raise to high:** In a running Composer: focus a Node T, link to it from Node A using the user-facing inline-link UI (`@` / `[label](dxn)`), and check whether A appears in T's "Related" panel. Also confirm the "Related" companion is visible by default for an arbitrary focused ECHO object.
- **Probe — show, on a unit, the set of units that link to it?:** YES — the "Related" panel lists Ref-property holders plus incoming Relation endpoints. Limit: computed only from first-class Ref props/Relations; markdown inline links (stored as text) are not enumerated (UNVERIFIED live); Text/hidden source types filtered out.
- **Probe — populated automatically without an authored return link?:** YES — automatic full-store scan; no manual return link required.

### UP-3.any-node-target — SUP — **partial** (confidence: medium)
When the structural successor is itself a first-class ECHO object (a Stack section, a Collection member with its own URI — `StackArticle.tsx:27-31`; `Collection.ts:17-31`), the user CAN link to that specific nested unit, and `Obj.getURI` resolves exactly that entity (`Obj.ts:512`; `entity-id.ts:99-103`) — **passes**. When the nested unit lives inside a document body as text — an outliner row (one Text blob, `Outline.ts:12-19`; `Text.ts:11-26`) or a markdown heading/block — the user can link only to the enclosing container; the row has no ECHO identity, no URI (`EID.ts:14-18`; `DXN.ts:16-31` carry no fragment), and is not enumerated by the picker (`useLinkQuery.ts:20-26`) — **fails**.
- **What would raise to high:** In a running Composer: open an Outline and a prose Markdown.Document, place the cursor on a nested row/heading, and exercise every "copy link"/link-creation affordance to confirm no gesture mints a sub-object URI resolving to that exact row/heading. Also confirm no installed plugin mints a first-class per-row/per-block object (Stack-style) for outliner/markdown content.
- **Probe — link to a specific bullet/block, or only a top-level container?:** Depends on modeling. First-class nested objects (Stack sections) CAN be linked; sub-document text units (outliner rows, markdown blocks) can link only to the enclosing container.
- **Probe — does the link resolve to that exact unit?:** YES for first-class nested objects (`Obj.getURI` names exactly that entity); NO for sub-document units (URI grammar has no fragment, so the finest resolvable target is the whole containing object).

### UP-4.edit-through — SUP — **pass** (confidence: medium)
The substrate keeps a single reactive instance per object id (`Database.getObjectById` is id-keyed, `Database.ts:127-130`; reactive atoms resolve to that one live object and update on mutation, `atoms.ts:187-238`; `Obj.update` notifies all subscribers, `Obj.ts:366-368`). Multi-location is real at the product layer: an object can be a member of N Collections via non-exclusive Refs (`Collection.ts:20-26`), and each Stack section live-resolves its ref via `Obj.atomReactive` (`StackArticle.tsx:224-229`), so an edit in one stack mutates the one underlying entity and is reflected wherever rendered. Independent copies arise only through the explicit `Obj.clone` (`Obj.ts:319-324`), never from multi-location rendering.
- **What would raise to high:** In a live Composer: add the same object to two Collections, open both stacks, edit content in one section, observe the edit appear in the other without reload. A passing end-to-end product test ("edit in A reflects in B") also raises it to high.
- **Probe — editing in one place updates the others, or independent copies?:** Updates the others — the same live object, not copies; single reactive instance per id, `Obj.update` notifies all subscribers; copies arise only via explicit `Obj.clone`.

### UP-4.embed — SUP — **pass** (confidence: medium)
The `![label](dxn)` block embed renders as an atomic inline block widget (`preview.ts:139-152,232-242`), produced via the `@@`/slash "Inline object" picker (`useLinkQuery.ts:57-64`). It binds to the live ECHO object via `client.graph.makeRef(dxn).target` (`MarkdownEditor.tsx:275`) and renders the Section surface — the identical Container the object uses standalone (`react-surface.tsx:40-55`) — so edits flow to the one underlying object and later changes to it reflect in the embed. Not a snapshot/copy.
- **What would raise to high:** In a live Composer: insert an `![label](dxn)` block embed into document A pointing at T; confirm T's content renders inline, type an edit into the inline-rendered T and confirm (a) the change persists to T (open T standalone) and (b) a separate change to T standalone appears in the embed. Settles the focus-guarded edit-mode nuance flagged at `MarkdownEditor.tsx:268-271`.
- **Probe — render a referenced unit inline (embed/transclude)?:** YES — `![label](dxn)` block embed as an atomic inline block widget portaling the resolved object's Section surface, produced via the `@@`/slash picker.
- **Probe — stays in sync and edits through, not a detached copy?:** YES (per code-reading) — binds to the live object and renders the same Container as standalone; edits flow to the one underlying object.

## 4. Cluster summary by primitive

**IP-1 (Node identity) — fully passes (substrate).** All four IP-1 reqs pass at the substrate. Every authored content unit is an `Obj` of `EntityKind.Object` with its own content-independent ULID `EntityId`, an open content-type set, and identity stable under edit/move/serialization. The Node primitive is present and well-formed at data-model altitude.

**IP-2 (structural edge) — the central gap.** `IP-2.direction` passes (reified `Relation` + directed Parent), but the multiplicity/acyclicity family does not conform as the spec models it. ECHO has **no type-distinct structural edge**: multi-predecessor placement and shared identity are achieved by **owner + reference** (non-owning Refs to one EntityId-keyed entity), the textbook *divergent* pattern (`IP-2.shared-identity` divergent; `IP-2.multi-predecessor` verifier-flagged toward divergent). And `IP-2.acyclic` is a hard **fail**: the only write-time acyclicity invariant lives on the single-owner inline-containment subgraph, which is structurally incapable of being the multi-predecessor edge — the multiplicity-capable mechanisms (Ref, Relation, parent) carry no acyclicity guarantee.

**IP-3 (linked edge) — fully passes (substrate).** Cross-reference (Ref, type-distinct from containment), may-cycle (cyclic Refs/reciprocal Relations admitted), backlinks (`referencedBy`/`ReverseRefIndex`, no stored back-edge), and inline expand (edit-through markdown block embed) all pass. The linked-edge primitive is present, with the latent note that ECHO offers *two* non-containment edge forms (Ref pointer vs reified Relation).

**UP-1 (outline / Node as user object) — uniformly partial.** Presentation of a nested outline exists (Outliner) and multi-location is real in the data model and navtree render, but two user-observable gaps recur: nested *content rows* have no per-Node addressing (capped by the fragment-less EID/DXN ceiling), and no user gesture co-locates an existing object into a second place without removing it from the first (`onCopy` disabled). Whole-object linking under edit/move passes; any-content-type parity passes.

**UP-2 (linking + backlinks view) — link passes, backlinks-view partial.** In-content linking is a shipped user capability (markdown `@`/slash). The backlinks *view* exists and auto-populates, but for first-class Ref/Relation edges — the user-authored inline markdown link is stored as text and plausibly does not feed it.

**UP-3 (granular addressing) — partial, mirrors IP-1 addressing ceiling.** Addressing splits exactly on how nesting is realized: first-class container membership is addressable; sub-document text structure is not, because no URI grammar reaches below whole-entity granularity.

**UP-4 (edit-through / embed) — fully passes (product).** Both edit-through across multi-location and inline embed/transclusion are shipped, user-observable, edit-through (not snapshot copies), grounded in the single-reactive-instance-per-id substrate.

## 5. Pattern classification

**Overall pattern: HYBRID — "different internal model" on the structural-edge family, "missing capability" on granular sub-Node addressing, with a strong conforming core.**

Justification, grounded in the verdicts:

- **Different internal model (divergent), on IP-2 structural multiplicity.** The system *delivers* the multi-location / one-shared-vertex capability at user-observable altitude (UP-4.edit-through pass; UP-1.multi-location's data-model/render half), but via **owner + reference** rather than the spec's first-class multi-predecessor structural edge. This is exactly the guide's Tana exemplar (`gap-analysis-guide.md:34`). `IP-2.shared-identity` is adjudicated **divergent**; `IP-2.multi-predecessor` is verifier-flagged as convention-conformantly **divergent** for the same reason. This is the dominant pattern across the structural-edge family.

- **Missing capability, on granular sub-Node addressing.** Independently of the model choice, there is a genuine capability gap: nothing in the whole system mints an address below whole-entity granularity (`IP-2.acyclic` fail on the multiplicity-capable edges; `UP-1.outline`, `UP-3.any-node-target`, and `UP-1.multi-location`'s user-gesture half all partial). The EID/DXN grammar has no fragment/path component, outliner rows are a Text blob, and the co-locate gesture is disabled. These are gaps at the user layer not rescued by any substrate equivalent.

- **Strong conforming core.** IP-1 (Node identity) and IP-3 (linked edge) pass fully at the substrate; UP-2.link, UP-1.stable-under-edit, UP-1.any-content-type, UP-4.edit-through, and UP-4.embed pass at the product. The Node-and-link half of the spec is met; the structural-DAG half is where divergence and missing capability concentrate.

This is not a pure "different internal model" (which would require the SUP to fully pass while only the SIP diverges) because real user-layer gaps remain (UP-1/UP-2/UP-3 partials); nor a pure "missing capability" (the conforming core is large and the multiplicity capability genuinely exists via another mechanism). Hence: hybrid.

## 6. Spec-improvement candidates

Every divergent and notable-partial verdict, with the `specFeedback` raised during adjudication. This section is for judging whether the **spec** (not X) needs revision.

**IP-2.multi-predecessor (verifier-flagged → divergent).** The req risks conflating a *capability* (native multiplicity / one-shared-vertex-in-many-locations) with one *storage mechanism* (a reified structural-edge entity). The feat preamble (line 9) and IP-2 desc (lines 105-107) assert the reified-edge mechanism, but `R-Conformance-Format` cl.1 (lines 28-36) declares the then-clauses sufficient and mandates they "read the same whether X stores the substrate as files, rows, or objects," excluding storage shape from the test. The two texts pull in opposite directions — the entire source of the pass-vs-divergent ambiguity. Recommend the spec state explicitly whether "reified edge entity" is a conformance criterion (→ belongs in a then-clause) or design rationale (→ stays in the preamble). Separately, then[1]'s "appears beneath each … in the outline" imports a rendering notion into a SIP invariant; it would read cleaner as a pure shared-successor invariant with "outline" rendering deferred to the SUP. (**Adopted 2026-07-11** — SIP then[1] reworded to a pure structural claim; see the IP-2.multi-predecessor re-review above.)

**IP-2.shared-identity (divergent).** The req's `given` ("a Node S with two or more structural PREDECESSORS") hardwires the IP-2.direction multi-predecessor-edge mechanism into the precondition for what is, at the then-clause, a pure edit-through/shared-identity invariant ("the same change is observed at every location where S appears"). This forces a divergent verdict on any substrate achieving multi-location by reference/membership (Tana, ECHO) even though the observable invariant fully holds. Consider restating the `given` at capability altitude — "a Node S that appears in two or more locations" — and letting the IP-2.direction dependency be carried by an explicit dependency note rather than baked into the precondition.

**IP-2.acyclic (fail — spec-sharpening note).** The req correctly states an invariant over "the set of structural edges," but adjudication exposed that ECHO's one hard acyclicity reject lives on a *different* object (single-owner inline containment) than any multiplicity-capable edge. The spec could note in the IP-2 dependency block that acyclicity and multi-predecessor are in tension for substrates that bundle their only acyclicity guarantee with single-ownership — i.e. flag that a conforming system must enforce acyclicity on the *same* edge type that carries multiplicity, not merely possess an acyclic single-parent tree somewhere.

**UP-1.outline (partial).** The req bundles two distinct concerns — (a) presentation of successors as a nested outline and (b) per-Node addressability including nested Nodes — and the system meets (a) but not (b). Per the one-concern-per-req convention these would adjudicate more cleanly as separate reqs (Outliner satisfies presentation but not addressing; Stack satisfies object-level addressing but not nesting). Clause (b) also largely restates UP-3.any-node-target; the overlap could be consolidated.

**UP-1.multi-location (partial).** The then-clause is phrased at outline altitude ("shown beneath each of its predecessors in the outline") but the only verified multi-predecessor mechanism is Collection membership in the navtree — whole-object-under-folder, not a content-outline Node nested beneath two parent Nodes within a document. Consider tightening the req (or the SIP IP-2 it traces) to state whether "structural predecessor" admits container/collection membership or requires in-document outline nesting.

**UP-2.link (pass — surface-assumption note).** Both then-clauses are phrased in DAG/outline terms ("A's outline is unchanged — T is not added as a successor of A"), presupposing the referrer's content is itself an outline of addressable Nodes. In Composer the in-content link affordance lives on a flat-Text markdown surface (so "outline unchanged" passes vacuously), while the only outline-structured surface (Outliner) has no object-link affordance. Consider splitting the capability (in-content linking) from the surface assumption (content is an outline of Nodes), so the "outline unchanged" invariant is tested where an outline actually exists.

**UP-2.backlinks-view (partial).** The then-clause is mechanism-agnostic about how A and C link to T, but UP-2 pairs it with UP-2.link, whose user-facing realization is the inline markdown link. The evidence exposes a seam: a backlinks view auto-populates for first-class Ref/Relation edges, yet the user-facing inline-link mechanism (text-embedded markdown link) may not feed it. The spec would be sharper if the req stated the view must include links formed by the *same* user-facing mechanism described in UP-2.link — otherwise a system can "pass" backlinks for a link type the user never authors while missing the type they do.

**UP-3.any-node-target (partial).** The `given` ("a structural successor of another Node") silently conflates two kinds of nesting the system treats very differently: (a) container-membership of first-class objects (passes exactly) and (b) sub-document text structure (fails — the unit has no identity). The req as written cannot be answered with one verdict without naming which nesting is intended. If the spec means to require addressing of sub-document units specifically (the canonical PKM "link to a bullet"), it should say so; otherwise a system passes on the container-membership reading while wholly failing the bullet-level reading.

**Non-divergent passes with latent spec notes (for completeness):** IP-1.content (scope "only" to authored-content-carrying entities so multi-kind substrates aren't ambiguous); IP-1.content-type (make explicit the test is on *openness* of the content-type set, examples non-normative); IP-1.stable-identity (split the persistence round-trip into its own probe/req); IP-2.direction (if the reified-edge requirement is load-bearing, make it an explicit then-clause); IP-3.cross-reference & IP-3.may-cycle (acknowledge the "linked edge" can map to either a property-held Ref pointer or a first-class Relation entity); IP-3.expand (note a system may realize cross-reference and embed as two render modes of the same reference); UP-1.any-content-type (distinguish the uniform-seam guarantee from per-type surface registration); UP-4.edit-through (widen the `given` to "a Node shown at two or more locations by any means"); UP-4.embed (phrase the `when` gesture-agnostically as "the user causes T to render inline" rather than "expands the link inline").
